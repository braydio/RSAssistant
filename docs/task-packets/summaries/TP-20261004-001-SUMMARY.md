## Dependency-refresh checkpoint (resolved)

TP-20261003-006 landed with these seam changes from what this packet originally assumed:

- `holdings_current` schema matches as assumed (account_id, ticker, quantity,
  price, position_value, account_total, observed_at, source).
- `refresh_id` is exposed, but the refresh lifecycle is **always a full
  replace** (`activate_staged_holdings` does `DELETE FROM holdings_current`
  then re-inserts everything from `holdings_refresh_staging` for that
  `refresh_id`), not an incremental per-account update. "Affected accounts"
  for a refresh is therefore *every* account present in the new current
  snapshot, which simplified the implementation: `record_account_value_snapshots()`
  aggregates straight off `holdings_current`/the staged rows rather than
  needing a separately-threaded list of touched accounts.
- No clean way existed to pass a python-side per-account aggregate into a
  `conn`-scoped call without re-deriving it from SQL, so the recommended
  signature `record_account_value_snapshots(conn, refresh_id, accounts,
  observed_at, source)` was adapted to make `accounts`/`observed_at` optional
  keyword args that default to aggregating `holdings_current` via `conn`
  directly. The historical backfill path still supplies `accounts` explicitly
  (and a `valuation_basis` override) since its data comes from
  `HistoricalHoldings`, not `holdings_current`.

## Effective-value rule

```text
positions_value = SUM(position_value) for the account's current positions
reported_account_total = the one distinct non-null account_total value
    for that account in this commit, or NULL if zero or more-than-one
    distinct non-null values are present
effective_value = reported_account_total if present, else positions_value
valuation_basis = "reported_total" | "positions_sum" | "historical_positions_sum"
```

## Conflicting account totals

Resolved via `COUNT(DISTINCT account_total)` per account per commit. Exactly
one distinct value is used as-is. Zero or more than one distinct value falls
back to `positions_sum` (logged as a warning naming the account and the
conflicting-value count) — never averaged, and never blocks the holdings
commit itself.

## Refresh transaction integration

Both `replace_current_holdings()` and `activate_staged_holdings()` call
`record_account_value_snapshots(conn, ...)` using the *same* `conn` and
`BEGIN IMMEDIATE` transaction that commits `holdings_current`. Verified by
test (`test_aborted_refresh_creates_no_snapshot`) that a staged-but-discarded
refresh never produces a snapshot, since it never reaches the commit path.

## HistoricalHoldings backfill

`backfill_historical_account_values()` groups `HistoricalHoldings` by
`(account_id, date)`, writes one row per group with deterministic
`refresh_id = "historical:<date>:<account_id>"`, `valuation_basis =
"historical_positions_sum"`, `reported_account_total = NULL`. Gated by a
`legacy_imports` row keyed `"historical_holdings_backfill"` — not yet run
against the real production database (only exercised in tests against
synthetic `HistoricalHoldings` rows); run it once, e.g. via a short Python
one-liner or a future ops script, to populate real history. Not wired to run
automatically on startup — left as an explicit, callable operation per the
packet's "capture data only" scope.
